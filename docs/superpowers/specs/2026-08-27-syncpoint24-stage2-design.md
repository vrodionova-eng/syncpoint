## Контекст

Этап 1 дал каркас и пять справочников: Пространства, Рабочие точки, Инструменты
с экземплярами, Услуги, Сотрудники. Этап 2 превращает справочники в рабочий
инструмент: **записи (бронирования)** на рабочие точки, **календарь**,
клиенты из CRM Битрикс24 и **расчёт зарплаты** сотрудников.

## Решения, принятые при brainstorm

| Вопрос | Решение |
|---|---|
| Макет календаря | **Вариант B — неделя одной точки**: сетка «неделя × часы» для выбранной рабочей точки; переключатель точки и недели сверху |
| Пересечение на точке | Жёсткая проверка — две записи на одну точку в одно время запрещены (409) |
| Нехватка инструментов | Мягкая проверка — предупреждение, запись сохранить можно |
| Цена записи | Авто-подстановка из услуг, всегда можно переопределить вручную |
| Клиент | Контакт CRM Б24: поиск по имени/телефону, создание нового; запись без клиента допустима |
| Роли/права | Не делаем (по ТЗ доступ не разграничиваем) |
| Длительность услуги / расписание точек | Не вводим — длительность записи задаётся вручную (start/end) |

## Модель данных

### Booking (Запись)
```
{
  id,
  workPointId: string,            // обязателен
  spaceId: string,                // копия из точки (снимок для фильтров/инструментов)
  start: string,                  // ISO-строка с таймзоной, обязателен
  end: string,                    // ISO-строка, обязателен, end > start
  employeeIds: string[],          // участники (≥ 1)
  serviceIds: string[],           // услуги (≥ 1)
  priceOverride: number | null,   // ручная сумма; null = считать из услуг
  priceTotal: number | null,      // итог: override ?? сумма услуг (снимок при сохранении)
  client: { contactId: number, name: string } | null,  // контакт CRM Б24
  toolInstanceIds: string[],      // забронированные экземпляры (снимок при сохранении)
  warnings: string[],             // предупреждения, показанные при сохранении (снимок)
  note: string | null,
  createdAt, updatedAt
}
```

Правила:
- `start`/`end` валидируются как даты; `end > start`; минимальная длительность 5 минут.
- `priceTotal` — снимок: сервер считает при создании/редактировании. Если
  `priceOverride` задан — берётся он; иначе сумма услуг:
  - простая `fixed` → `price`;
  - простая `range` → `priceMin` (консервативно, точная сумма вводится override);
  - составная `auto` → сумма под-услуг (range складывается по min);
  - составная `fixed` → `price`;
  - составная `manual` → 0 (ожидается override).
- Если хотя бы одна услуга `range`/`manual` и override не задан — `priceTotal`
  считается по min, а в ответе возвращается `priceEstimated: true` (фронт
  подсвечивает «цена ориентировочная»).
- `toolInstanceIds` и `warnings` заполняет сервер при сохранении (см. ниже).
- Удаление записи — свободное. Удаление сущностей справочников, на которые
  ссылается хотя бы одна запись, блокируется (`ConflictError`):
  точка, сотрудник, услуга, экземпляр инструмента.

### Employee.salary (задел Этапа 1 получает UI)
```
salary: {
  mode: "flat" | "perService" | null,
  flatPercent: number | null,        // 0–100, для mode=flat
  servicePercents: [{ serviceId, percent }]  // для mode=perService
}
```

## Проверки при сохранении записи

### Жёсткая: пересечение рабочей точки
Две записи конфликтуют, если `workPointId` совпадает и интервалы пересекаются
(`a.start < b.end && b.start < a.end`). Конфликт → `409 ConflictError` с текстом
«Точка занята: с HH:MM до HH:MM». При редактировании запись не конфликтует сама
с собой.

### Мягкая: подбор экземпляров инструментов
Для каждого инструмента-вида из `requiredToolIds` всех услуг записи:
1. Кандидаты — экземпляры этого инструмента со `spaceId` = пространству точки
   **или** `spaceId = null` (общие).
2. Занятые — экземпляры, попавшие в `toolInstanceIds` других записей,
   пересекающихся по времени.
3. Берётся первый свободный (детерминированно: по `createdAt`).
4. Свободного нет → предупреждение «Не хватает инструмента "X" для услуги "Y"»,
   запись всё равно сохраняется.

Результат фиксируется в `toolInstanceIds`/`warnings` записи. Это **снимок**:
если позже соседние записи изменятся, пересчёт происходит только при повторном
сохранении этой записи. Гонки двух одновременных сохранений допустимы (последний
записавший выигрывает) — объёмы маленькие, блокировки не вводим.

## API

Новые маршруты (монтируются в `server.js`):

```
GET    /api/bookings?from=<ISO>&to=<ISO>&workPointId=<id>&spaceId=<id>
POST   /api/bookings
GET    /api/bookings/:id
PUT    /api/bookings/:id
DELETE /api/bookings/:id

GET    /api/b24/crm/contacts?query=<строка>   → [{ id, name, phone }]
POST   /api/b24/crm/contacts  { name, phone? } → { id, name }

PUT    /api/employees/:id/salary  { mode, flatPercent?, servicePercents? }

GET    /api/payroll?from=<ISO>&to=<ISO>  → расчёт ЗП (см. ниже)
```

### Ответ create/update записи
```
{ booking, priceEstimated: boolean, warnings: string[] }
```
`warnings` дублирует снимок записи — фронт показывает их сразу после сохранения.

### Расчёт ЗП (`/api/payroll`)
Для каждого сотрудника, участвовавшего в записях за период:

- `mode = flat`: `sum(priceTotal записей сотрудника) × flatPercent / 100`.
- `mode = perService`: по каждой записи доля сотрудника считается по услугам:
  сумма по услугам записи `price(service) × percent(service) / 100`. Услуги без
  индивидуального процента дают 0. Если у записи задан `priceOverride`, он
  распределяется на услуги пропорционально их ценам по умолчанию (range → min);
  если сумма по умолчанию 0 — override делится поровну между услугами.
- `mode = null`: сотрудник попадает в ответ с `amount = null` («схема не задана»).

Несколько участников одной записи: сумма записи **не делится** между ними —
каждому начисляется его процент от полной суммы (типичная схема «мастер +
помощник» регулируется самими процентами).

Ответ:
```
{ from, to, rows: [{ employeeId, name, mode, bookingsCount, turnover, amount }] }
```
`turnover` — сумма `priceTotal` записей сотрудника за период (до процентов).

## Фронтенд

Новые вкладки SPA: **«Календарь»** (становится первой и открывается по умолчанию)
и **«Зарплата»**. Вкладки справочников остаются.

### Календарь (вариант B — неделя одной точки)
- Шапка: переключатель рабочей точки (select), кнопки «‹ неделя ›», кнопка
  «Сегодня», кнопка «+ Запись».
- Сетка: колонки Пн–Вс (с датами), строки — часы 08:00–21:00 (шаг 30 мин).
  Блок записи занимает высоту пропорционально длительности; текст: время,
  услуги, клиент.
- Клик по записи — карточка/редактирование. Клик по пустой ячейке — новая
  запись с предзаполненными точкой и временем.
- Цвет записи выбирается по первому сотруднику (детерминированный набор из ~8
  цветов по хешу id).
- Запись с `warnings` отмечается значком ⚠ (title — текст предупреждений).

### Форма записи (модалка)
Поля: точка (подставлена из календаря), дата, время начала/конца, участники
(чекбоксы сотрудников), услуги (мультиселект), цена (автоподстановка суммы,
редактируемая; признак «изменено вручную»), клиент (поиск по CRM с созданием
нового контакта; поле необязательное), заметка.
При сохранении: конфликт точки → сообщение об ошибке в форме; предупреждения по
инструментам → показываются подтверждением «сохранить всё равно?» (второй клик
по «Сохранить» с флагом `ackWarnings: true`).

### Зарплата
- Фильтр периода (дата от/до, по умолчанию текущий месяц).
- Таблица: сотрудник, схема, записей, оборот, начислено.
- Настройка схемы — в карточке сотрудника (вкладка «Сотрудники»): режим
  «общий %» / «% по услугам», поля процентов.

## Тестирование

- Юнит-тесты `bookingsService`: валидация дат/участников/услуг; жёсткий конфликт
  точки (включая редактирование — нет самоконфликта); подбор экземпляров
  (приоритет своего пространства, fallback на общие, нехватка → warning);
  расчёт `priceTotal` по всем режимам услуг; override.
- Юнит-тесты `payrollService`: flat, perService (включая override и деление
  поровну при нулевой базе), mode=null, несколько участников.
- Тесты маршрутов: CRUD записей, 409 на пересечение, salary endpoint, payroll
  endpoint, CRM-контакты с замоканным VibeCode-клиентом.
- Существующие тесты ссылочной целостности дополняются: блокировка удаления
  сущностей, занятых в записях.
