# SyncPoint24 — Этап 1: Справочники и каркас. Дизайн

**Дата:** 2026-06-04
**Статус:** утверждён к реализации
**Этап:** 1 из 2

---

## Контекст

SyncPoint24 — система бронирования ресурсов внутри Битрикс24, открывается пунктом
в левом меню портала. Бронируется **рабочая точка** на отрезок времени. Рабочая
точка находится в пространстве; нужные для услуги инструменты берутся (и условно
бронируются) из экземпляров этого же пространства. У записи есть сотрудники
(несколько участников через чекбоксы — задел под расчёт ЗП), услуга(и), цена и
клиент из CRM Б24.

Проект разбит на два этапа:

- **Этап 1 (этот спек):** каркас приложения внутри Б24 + бэкенд с хранилищем +
  пять справочников (Пространства, Рабочие точки, Инструменты с экземплярами,
  Услуги, Сотрудники). Без календаря и записей.
- **Этап 2 (отдельный спек):** календарь, записи на рабочие точки, проверка
  пересечений, чекбоксы участников, клиенты из CRM, экран настройки ЗП и расчёт.

Цель Этапа 1 — работающий продукт, в котором можно полностью завести всю
справочную базу. Это фундамент, на котором Этап 2 строит календарь.

## Решения, принятые при онбординге

| Вопрос | Решение |
|---|---|
| Что бронируется | Рабочая точка; экземпляры инструментов привязаны к пространству (не к точке) |
| Клиент записи | Из CRM Битрикс24 (релевантно для Этапа 2) |

| Авторизация | Отдельной нет — доступ через Б24 |
| Стиль | Битрикс24 (`theme-b24.css`) |
| Настройка схемы ЗП | В Этапе 1 — только задел в данных, без UI |
| Термин для физической штуки инструмента | «Экземпляр» |

## Архитектура

### Размещение в Битрикс24

- Приложение регистрируется как пункт **левого меню** портала (placement `LEFT_MENU`).
- Б24 открывает приложение в iframe и отправляет `POST /` с данными о размещении.
- Сервер отвечает на `POST /` и `GET /` одинаково — отдаёт `index.html`
  (паттерн из CLAUDE.md: Б24 iframe).
- Подключение к Б24 на Этапе 1 нужно ровно для одного: подтянуть список
  пользователей портала во вкладку «Сотрудники». Работа с CRM — Этап 2.

### Слои

```
Браузер (iframe в Б24)
  └─ src/public/  — vanilla JS + CSS (тема Б24), SPA «Настройки» с вкладками
        │  fetch → /api/*
        ▼
Express (src/server.js)
  ├─ routes/      — REST-маршруты на каждую сущность (тонкие, без логики)
  ├─ services/    — бизнес-логика и валидация
  └─ repositories — чтение/запись JSON-файлов, по одному модулю на сущность
        ▼
Хранилище: JSON-файлы на диске + кеш в памяти (Map)
  ├─ локально: data/
  └─ на сервере Vibecode: /opt/data/   (переживает чистый деплой)
```

### Хранилище

- Каждая сущность — отдельный JSON-файл в каталоге данных
  (`spaces.json`, `work-points.json`, `tools.json`, `tool-instances.json`,
  `services.json`, `employees.json`).
- При старте репозиторий читает файл в память (Map по id). Запись — синхронно
  обновляет Map и атомарно перезаписывает файл (через temp-файл + rename).
- Каталог данных берётся из переменной окружения `DATA_DIR`
  (локально `./data`, на проде `/opt/data`), по умолчанию `./data`.
- Внешняя БД не используется — для справочников объём мал, JSON достаточно.

## Модель данных

Все id — строковые (короткий случайный идентификатор, генерируется на сервере).
У всех сущностей есть `createdAt`, `updatedAt` (ISO-строка).

### Space (Пространство)
```
{ id, name, createdAt, updatedAt }
```

### WorkPoint (Рабочая точка)
```
{ id, name, spaceId, createdAt, updatedAt }
```
- `spaceId` — обязателен, ссылается на существующее Пространство.

### Tool (Инструмент) — вид/тип
```
{ id, name, createdAt, updatedAt }
```

### ToolInstance (Экземпляр инструмента) — конкретная физическая штука
```
{ id, toolId, spaceId | null, label | null, createdAt, updatedAt }
```
- `toolId` — обязателен.
- `spaceId` — необязателен (`null` = экземпляр не привязан к пространству, общий).
- `label` — необязательная подпись («Фен №1»), для удобства в списках.
- В одном пространстве может быть несколько экземпляров одного инструмента
  (несколько `ToolInstance` с одинаковым `spaceId`).
- Сценарий: создаёшь инструмент «Фен» и задаёшь распределение по пространствам —
  напр. Пространство А = 2, Пространство Б = 4 → сервер создаёт 6 экземпляров
  (2 со `spaceId` А, 4 со `spaceId` Б). Распределение можно потом менять:
  добавлять/удалять экземпляры по пространствам.

### Service (Услуга)
```
{
  id, name,
  priceType: "fixed" | "range",
  price: number | null,            // для fixed
  priceMin: number | null,         // для range
  priceMax: number | null,         // для range
  isComposite: boolean,            // состоит ли из под-услуг
  childServiceIds: string[],       // для составной
  compositeSum: "auto" | "fixed" | "manual",  // как считать сумму составной
  requiredToolIds: string[],       // какие инструменты (виды) нужны для услуги
  createdAt, updatedAt
}
```
Правила цены (какие поля применимы — зависит от `isComposite`):
- **Простая услуга** (`isComposite = false`): применимы `priceType` + `price`
  (для `fixed`) или `priceMin`/`priceMax` (для `range`). Поля `compositeSum`,
  `childServiceIds` не применяются: `compositeSum = null`, `childServiceIds = []`.
- **Составная услуга** (`isComposite = true`): `priceType`, `priceMin`, `priceMax`
  **не применяются** (`priceType = null`), цену определяет `compositeSum`.
  Задаётся список `childServiceIds` и способ суммы:
  - `auto` — сумма цен под-услуг (для range суммируются мин и макс отдельно);
    поле `price` не используется;
  - `fixed` — своя цена указывается сразу в настройке (поле `price`);
  - `manual` — цена не фиксируется, вводится при записи (Этап 2); `price = null`.
- Сервер валидирует консистентность: заполнены ровно те поля, что применимы для
  выбранного режима; лишние — отвергаются или зануляются.
- Запрет циклов: составная услуга не может прямо или косвенно включать саму себя.
- **Важно (поведение Этапа 2):** цена услуги — это лишь значение по умолчанию.
  Итоговую сумму записи всегда можно переопределить вручную при бронировании,
  независимо от типа цены услуги. На модель справочника услуг это не влияет.

Требуемые инструменты:
- `requiredToolIds` — список **инструментов-видов** (не экземпляров), которые
  нужны для услуги. Пространство здесь не указывается.
- В Этапе 2 эти инструменты автоматически подставляются в запись и система
  пытается забронировать их экземпляры (см. ниже).

### Employee (Сотрудник)
```
{
  id, name,
  source: "b24" | "manual",
  b24UserId: number | null,        // заполнен если source = b24
  salary: {                        // ЗАДЕЛ под Этап 2 — без UI в Этапе 1
    mode: null,                    // позже: "flat" | "perService"
    flatPercent: null,             // позже: число
    servicePercents: []            // позже: [{ serviceId, percent }]
  },
  createdAt, updatedAt
}
```
- `source = b24` — подтянут из Б24, хранит `b24UserId` и имя на момент загрузки.
  `b24UserId` уникален: повторный импорт того же пользователя не создаёт дубль
  (существующая запись пропускается, имя при желании обновляется).
- `source = manual` — добавлен вручную, только имя; `b24UserId = null`.
- Блок `salary` создаётся пустым и в Этапе 1 не редактируется (нет экрана).
  Структура заложена, чтобы Этап 2 не менял формат данных.

### Связи и ссылочная целостность

- Рабочая точка → Пространство (обязательно).
- Экземпляр → Инструмент (обязательно), → Пространство (необязательно; `null` =
  общий экземпляр, доступен в любом пространстве).
- Составная услуга → под-услуги (список).
- Услуга → требуемые инструменты (`requiredToolIds`, список инструментов-видов).
- Удаление сущности, на которую есть ссылки, **блокируется** с понятным
  сообщением. Без каскадного удаления. Конкретно:
  - Пространство нельзя удалить, если в нём есть рабочие точки или экземпляры.
  - Инструмент нельзя удалить, если у него есть экземпляры или он указан в
    `requiredToolIds` хотя бы одной услуги.
  - Услугу нельзя удалить, если она входит в `childServiceIds` другой услуги.

## API (REST)

Базовый префикс `/api`. Формат — JSON. Ответы:
`{ ok: true, data }` или `{ ok: false, error: { message, code } }`.

Стандартный CRUD на каждый справочник:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/spaces` | список пространств |
| POST | `/api/spaces` | создать |
| PUT | `/api/spaces/:id` | изменить |
| DELETE | `/api/spaces/:id` | удалить (с проверкой ссылок) |
| … | `/api/work-points` | то же для рабочих точек |
| … | `/api/tools` | GET/PUT/DELETE для инструментов (POST — особый, см. ниже) |
| … | `/api/tool-instances` | то же для экземпляров (поштучно) |
| … | `/api/services` | то же для услуг |
| … | `/api/employees` | то же для сотрудников |

**Инструмент и его экземпляры** — разделение ответственности:
- `POST /api/tools` создаёт инструмент сразу с начальным распределением экземпляров
  (это единственный POST для инструмента, тело с `distribution` — см. ниже).
- Дальнейшее добавление/удаление **отдельных** экземпляров — через CRUD
  `/api/tool-instances` (создать один, удалить один, сменить пространство).
- `PUT /api/tools/:id` меняет только сам инструмент (имя), не трогая экземпляры.

Особые маршруты:

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/tools` | создать инструмент + экземпляры по пространствам (тело: `{ name, distribution: [{ spaceId\|null, count }] }`) |
| GET | `/api/b24/users` | получить пользователей портала из Б24 (прокси к VibeCode API) |
| POST | `/api/employees/import` | импорт сотрудников из выбранных пользователей Б24 (пропускает уже импортированных по `b24UserId`) |
| GET | `/api/health` | проверка живости |

## Фронтенд

Одностраничное приложение «Настройки» с боковыми вкладками:

**Пространства · Рабочие точки · Инструменты · Услуги · Сотрудники**

Каждая вкладка:
- список записей (карточки/строки) с действиями «Изменить» / «Удалить»;
- кнопка «Добавить» → форма создания (модалка или боковая панель);
- inline-валидация (обязательные поля, корректность ссылок).

Особенности вкладок:
- **Рабочие точки:** при создании — выбор пространства из выпадающего списка.
- **Инструменты:** при создании — распределение экземпляров по пространствам
  (строки «пространство + количество», можно строку «без пространства» = общий).
  После создания инструмент показывает список своих экземпляров; распределение
  можно менять (добавлять/удалять экземпляры по пространствам).
- **Услуги:** переключатель «Простая / Составная»; для простой — фикс/диапазон;
  для составной — выбор под-услуг (мультиселект) + способ суммы; превью итоговой
  цены при `auto`. Отдельный блок «Нужные инструменты» — мультиселект инструментов
  (`requiredToolIds`), без указания пространства.
- **Сотрудники:** две кнопки — «Загрузить из Битрикс24» (список пользователей
  портала с чекбоксами → импорт) и «Добавить вручную» (только имя). В списке
  виден источник (бейдж «Б24» / «вручную»).

Технологии: vanilla JS + CSS, тема `theme-b24.css`, CSS custom properties для
цветов и отступов. Без фреймворков (паттерн CLAUDE.md).

## Обработка ошибок

- API всегда возвращает структурированный ответ `{ ok, data | error }`.
- Валидация на сервере (источник истины): обязательные поля, существование
  ссылок, запрет удаления при наличии зависимостей, запрет циклов в составных
  услугах.
- Фронт показывает сообщения об ошибках понятным языком, рядом с полем/действием.
- Ошибки обращения к Б24 (`/api/b24/users`) не ломают приложение: вкладка
  «Сотрудники» продолжает работать с ручным добавлением, показывается баннер
  «Не удалось загрузить пользователей Б24, попробуйте позже».
- VibeCode API может возвращать данные в `data.result` или `data.data` —
  обёртка проверяет оба формата (паттерн CLAUDE.md).

## Тестирование

- **Юнит-тесты бизнес-логики (services):** валидация полей цены по режиму
  (простая/составная), расчёт суммы составной услуги (`auto` для fixed и range),
  запрет циклов, блокировка удаления при ссылках (в т.ч. инструмент в
  `requiredToolIds` услуги), создание инструмента с распределением экземпляров
  по пространствам, дедупликация импорта сотрудников по `b24UserId`.
- **Тесты репозиториев:** запись/чтение, атомарность перезаписи файла,
  изоляция через временный `DATA_DIR`.
- **Тесты маршрутов:** happy-path CRUD на каждую сущность + ключевые ошибки
  (404, валидация, конфликт удаления) через supertest.
- **Smoke:** `npm run check` — подключение к VibeCode API («API connection OK»).
- Б24-прокси (`/api/b24/users`) тестируется с замоканным API-клиентом.

## Что НЕ входит в Этап 1

Явно вне объёма (это Этап 2):

- Календарь и сами записи (бронирования).
- Проверка пересечений по точкам и экземплярам инструментов.
- Чекбоксы участников-сотрудников в записи.
- Клиенты и сделки из CRM Б24.
- Экран настройки схемы ЗП и расчёт зарплаты.
- Переопределение итоговой суммы записи вручную (цена услуги — лишь значение по умолчанию).
- Авто-подстановка нужных инструментов услуги в запись и бронирование их
  экземпляров: при сохранении записи система берёт свободный экземпляр нужного
  инструмента из пространства рабочей точки (или общий экземпляр со `spaceId = null`).
  Если все экземпляры на это время заняты — показывается **предупреждение**
  «не хватает инструмента "X" для услуги», но запись всё равно можно сохранить
  (мягкая проверка, не блокирующая).
- Роли и разграничение прав.
